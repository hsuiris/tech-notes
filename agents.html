理解多代理協作

01

八種常見工作流程

02

資料分工與相互審查的差異

平行分工接循序處理

分別蒐集，再統一分析

來源 A／B／C → 資料整合 → 分析 → 報告
適用條件
資料來源與任務範圍可事先劃分，子任務不需頻繁交換資訊。
主要效益
獨立查詢可以同時執行。整合前需檢查資料覆蓋範圍、重複內容與引用。
限制
若分工有遺漏，後續分析未必能察覺。整合者需要對照原始問題驗收。
平行產出接相互審查

交換論證，再修訂結論

獨立報告 A／B／C → 相互檢查 → 修訂與整合
適用條件
希望檢查不同假設、證據或推理，且有足夠預算進行多輪處理。
主要效益
其他代理可能指出缺漏或矛盾。評估時應記錄哪些問題因此被修正。
限制
共享資料與模型偏誤可能讓代理一起接受錯誤。最後仍需查核證據。
兩種流程可依任務組合。例如先平行蒐集資料，只針對有爭議的結論加入審查。實際效益應與較簡單的流程比較，並同時記錄成本與耗時。
03

投票、辯論與評估如何收斂結果

比較這些方法時，可先看答案是否互相可見，再看最後如何選擇或生成結果。

方法 資訊如何流動 結果如何產生 需要留意
Voting投票 各次取樣先獨立回答 依多數決等規則彙整 共同偏誤可能使多數答案也出錯
Debate辯論 交換回答與理由後修訂 依規則投票、整合或評選 相互說服不代表證據更充分
Mixture-of-Agents多代理整合 後續模型參考前層的回答 重新生成一份整合內容 整合可能遺漏分歧或混合矛盾資訊
LLM-as-Judge模型評估 評估模型閱讀待評內容與標準 評分、比較、排序或選擇 須驗證評分與人工判斷是否一致
Evaluator-Optimizer評估與修訂 產出端接收評估意見 修訂至達標或停止條件成立 應限制回合，避免反覆修改

以模型評分作為改善目標時，產出可能逐漸迎合評分方式。例如增加篇幅可能提高評分，卻沒有補上證據。因此，應將事實、引用與需求完成度分別檢查，並保留人工抽查。

評估也可能受到答案順序影響。可交換候選答案順序再評估，觀察結果是否穩定。這是檢查偏差的方法，不能保證消除所有評估錯誤。

Token 是模型處理文字的計量單位，不能直接換算成中文字數或固定費用。評估自己的流程時，應量測任務完成品質、實際 token 用量與端到端耗時，並保留相同題目的單代理基準。

05

分工之前先檢查限制

共享內容過多

若每個代理都必須閱讀相同的大量資料，重複輸入與協調成本可能抵銷平行處理的收益。可先評估單代理能否完成。

任務彼此依賴

共同修改同一組程式或資料時，需要明確邊界與整合流程。獨立檔案審查可以分工，高度相依的修改則未必適合。

需要頻繁同步

代理之間的溝通能力取決於實作。若每一步都要等待其他代理回覆，平行執行可能沒有明顯效益。

單代理已符合需求

若品質與耗時已達標，新增代理應有可量測的改善目標，例如提高資料覆蓋率或縮短特定階段的等待。

常見問題與改善方式

分派過多子任務

依任務難度設定代理數、工具呼叫與 token 預算。記錄追加任務的理由，避免簡單查詢持續擴張。

範圍重疊或遺漏

分派時寫清楚負責範圍、必要來源與輸出格式。整合時逐項對照需求，確認是否仍有缺口。

來源品質不足

要求優先查閱原始文件、官方資料或研究全文。搜尋排名只能協助發現資料，不能代替可信度判斷。

重要資訊未被保留

上下文容量依模型而異，通常以 token 計算。保存中間成果與來源，摘要時保留限制條件，避免後續處理失去依據。

論文 Why Do Multi-Agent LLM Systems Fail? 將失敗整理為系統規格、代理間協調，以及驗證與終止等類別。排查時可分別確認任務是否定義清楚、交接是否完整、驗收是否確實執行。這套分類不代表所有問題都能只靠修改提示解決。
