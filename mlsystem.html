02

六項設計取捨

即時與批次推論

即時推論收到請求後計算，能使用當時可取得的資料。
批次推論預先計算並保存結果，查詢時直接讀取。

先定義結果更新頻率。若每日更新已符合用途，可測試批次方案；需要回應即時狀態的任務則可能需要線上計算。成本差異應以實際流量與資源估算。

模型規模

較大模型可能具備較廣的能力，也需要評估資源與延遲。
較小模型資源需求可能較低，特定任務也可能有良好表現。

以代表性資料比較品質、延遲與成本。可考慮分流，但必須驗證分流條件，不能直接把模型自述的信心當作可靠機率。

外部 API 與自行部署

外部 API由供應商管理模型服務，依使用方式計費。
自行部署自行管理模型、硬體與服務生命週期。

自行部署既有模型與自行訓練是不同決策。比較時納入資料限制、用量、硬體利用率與維運人力，不只比較 API 帳單。

品質與延遲

品質目標以任務指標與錯誤案例評估。
延遲目標設定端到端與高百分位的等待上限。

在同一工作負載下比較方案，找出符合品質與等待需求的組合。刪減步驟之前，確認它對品質或驗證是否必要。

資料新鮮度

頻繁更新反映較近期的事件，增加資料管線要求。
週期更新依固定週期處理，流程可能較容易管理。

區分原始資料、特徵與模型的更新頻率。以新舊資料對結果的影響決定需求，並監控延遲與缺漏。

誤判與漏判

偽陽性把不符合條件的樣本判為符合。
偽陰性沒有辨識出實際符合條件的樣本。

固定模型的判定門檻會影響兩類錯誤，但改善資料或模型可能同時改善兩者。應依實際損失、申訴機制與人工處理能力選擇門檻。

RAG 的資料準備與查詢流程

RAG（Retrieval-Augmented Generation，檢索增強生成）先取得相關資料，再讓模型參考資料生成回答。下方是常見的向量檢索流程；前三步準備索引，後三步處理查詢。點選各步查看說明。

選擇一個階段，查看處理內容與檢查方向。

RAG 的錯誤可能發生在文件解析、檢索、權限過濾或生成階段。
先檢查取得的資料是否足以回答，再確認模型是否正確引用與解讀。這有助於縮小問題範圍。
