Claude 技能

自己做一個 Claude 技能

01

一個外掛裡面，最多只有五種零件

名字看起來很多：skill、command、agent、hook、MCP。它們的差別只有一個：誰去叫它。點左邊任何一個看說明。

← 點左邊任何一個，這裡會說明它是什麼、放在哪、你已經在用的例子。

換成生活裡的東西：skill 是知識（要用的時候自己想起來）、command 是按鈕（你按才動）、agent 是員工（派出去自己做完）、hook 是鬧鐘（時間到自己響）、MCP 是插座（接外面的東西）。
plugin（外掛）不是第六種零件，它只是一個把上面五種裝在一起、可以整包送人的資料夾。

那它們實際上住在哪？

五種零件不是抽象概念，每一種都是硬碟上一個看得到的檔案。下面就是實際的 ~/.claude/ 資料夾長什麼樣。前三種各有自己的資料夾，後兩種是寫進設定檔裡的一段文字。

~/.claude/ ← 個人設定，所有專案通用 ├── skills/ ← skill 全部放這裡 │ └── tw-tech-blog-voice/ ← 一個技能 ＝ 一個資料夾 │ ├── SKILL.md ← 檔名固定，全大寫 │ └── word-swaps.md ← 要查才讀的長資料 │ ├── commands/ ← command 全部放這裡 │ └── review-code.md ← 打 /review-code 跑的就是它 │ ├── agents/ ← agent 全部放這裡 │ └── coder.md ← 派出去寫程式的那個分身 │ └── settings.json ← hook 寫在這個檔案裡面 專案資料夾/ └── .mcp.json ← MCP 接哪些外部服務，寫這裡

看這張圖要抓三件事

一、skill 是資料夾，command 跟 agent 是單一檔案。所以 skill 可以帶著附件（像上面的 word-swaps.md），另外兩個不行，只能一個 .md 寫完。

二、hook 跟 MCP 沒有自己的資料夾。它們是設定檔裡的一段文字，不是獨立檔案。這也是為什麼它們最容易寫錯又最難查，因為錯了不會有檔案不見，只是安靜地不動作。

三、放在 ~/.claude/ 是全域，放在專案裡的 .claude/ 是只有那個專案有。兩邊結構一模一樣。自己的習慣放全域，跟團隊共用的規矩放專案裡跟著 Git 走。

agent 要怎麼做？跟 skill 一樣嗎？

寫法幾乎一樣，都是一個純文字檔加上開頭那塊標籤。差別只有兩個：多一行 tools，以及內文是寫給「另一個新開的 Claude」看的。

--- name: coder description: 要新建或修改程式碼 ← 跟 skill 一樣 的任務都派給它。 tools: Read, Write, Edit, Bash ← skill 沒有這行 --- 你是本團隊的工程師，務實、直言、 ← 這裡開始是 極度重視程式碼品質⋯⋯ 它的角色設定 存成 ~/.claude/agents/coder.md，重開就生效

最重要的是 tools 那行

agent 給它什麼工具，它就只能用什麼。上面這個有 Write 跟 Edit，所以它改得動檔案。如果你做一個只負責查資料的 agent，就不要給它 Write，那它連想改也改不了。

這是 skill 做不到的事。skill 是規則，規則可以被說服；agent 沒有那個工具就是沒有，講什麼都沒用。

另一個差別是記憶。skill 在你現在的對話裡，看得到前面聊過什麼。agent 是開一個全新的，只看得到你派給它的那段話，做完只回報結論。好處是過程不佔你的畫面，壞處是你要交代得夠清楚，它沒辦法回頭問你。

02

常見的 Skill 架構

常見的技能架構大致有四種，差別在於除了規則以外還帶了什麼。

最常見

只有規則

資料夾裡就一個 SKILL.md，沒有別的
  • 它不「做」事，只是規定 Claude 要怎麼做
  • 可以寫得很長，最長的一個 1465 行，一行程式都沒有
  • 沒有程式，所以不會壞、不用維護
例：imagegen-frontend-web（987 行，規定網頁設計稿長什麼樣）、ponytail（100 行，逼它寫最少的程式）
內容太多時

規則 ＋ 查表

多一個 references/ 資料夾
  • 常用的規則寫在 SKILL.md，厚重的對照表另外放
  • 要查的時候才去讀，平常不佔位子
  • 怎麼分？這份資料你自己也不會背，只會查，那就放這裡
例：elon-musk-perspective（429 行規則 ＋ 6 個檔的訪談語料）、3-statement-model（408 行 ＋ 財報範本）
不能靠猜時

規則 ＋ 程式

多一個 scripts/ 資料夾
  • 裡面是真的會被執行的程式碼
  • 用在不能靠猜的事：算數字、轉檔、抓網頁
  • 代價是它會壞，環境變了要修
例：watch（下載影片、切影格、抓字幕）、dcf-model（1264 行 ＋ 驗算程式）
最進階

會派分身

內容裡會叫 Claude 開別的 Claude 去做
  • 把大工作拆給好幾個分身同時做
  • 每個分身只回報結論，不佔你的畫面
  • 用在「同一件事要做很多次」或「要交叉驗證」
例：verify-answers（派一批分身各自重算答案再比對）、faceless-explainer（分鏡、配音、字幕分頭做）
怎麼選：從第一種開始，不夠再往下加。大部分技能到最後都還只是一個 .md 檔，一輩子沒用到後面三種。
加東西的順序是固定的：規則寫不清楚 → 加 references/；有事情不能靠猜 → 加 scripts/；同一件事要重複做很多次 → 才需要派分身。

挑三個拆開來看

下面三個是網路上抓得到的現成技能，任何人都能裝。它們剛好一個是「只有規則」，一個是「規則＋程式」，一個是把很多 skill 包成一整包。

~/.claude/skills/ └── imagegen-frontend-web/ └── SKILL.md ← 就這一個檔
1個檔案
987行純文字
0行程式碼

這是什麼：叫 AI 畫網頁設計稿的技能。你說「幫我做一個賣咖啡的網站」，它就照規矩產出一張張設計圖。

它其實沒有「做」任何事，它只是規定

987 行裡面一行程式都沒有。全部是寫給 Claude 看的硬規則，而且寫得很兇。實際內容：

一個 section（網頁的一個區塊）就出一張圖。 8 個 section 就是 8 張圖。永不合併成一張。 這條規則蓋過模型本來想偷懶的預設行為。

為什麼要寫得這麼兇？因為 Claude 有自己的懶惰習慣（它會想把 8 個區塊擠成一張長圖）。這種外掛的價值不在功能，在於「把品味變成不能討價還價的條文」，像是「左文字右圖片是最爛的 AI 老套版型，不准當第一選擇」。

你可以偷學：真正值得做成 skill 的，是那種你心裡有一套標準、但每次都要重講一遍的事：做網站的版型品味、影片要抓哪幾種畫面、報告一定要有哪幾段、資料要驗到什麼程度才算數。
反過來說，一句話交代得完的小事就不要做成 skill（「這次不要用 emoji」直接講就好）。大概的門檻是：你講過三次以上，而且每次都要講超過五句，才值得寫成一份。
financial-analysis/ ├── .claude-plugin/ │ └── plugin.json ← 身分證 ├── commands/ 7 個 /指令 │ ├── dcf.md │ ├── comps.md │ └── … ├── skills/ 13 個技能 │ ├── dcf-model/ │ │ ├── SKILL.md 1263 行 │ │ ├── references/ 要用才讀 │ │ └── scripts/ 驗算用 │ └── … ├── hooks/hooks.json （空的） └── .mcp.json 接 11 家資料商
13個 skill
7個 command
11個外接資料源

這是什麼：Anthropic 自己出的財務分析工具包。你說「幫我估 Nvidia 值多少錢」，它會抓財報、找同業比較、做出一份 Excel 估值報告。

command 當總機，skill 當專業

打 /dcf 的時候，那個檔案自己不做任何計算。它做的事是排流程，然後把工作丟給別的 skill：

第 2 步 → 先叫 comps-analysis 這個 skill， 找 4~6 家同業、抓出中位數倍數 第 3 步 → 再叫 dcf-model 這個 skill， 用剛剛那些數字當假設去估值 第 4 步 → 拿兩邊結果互相對照，差太多就回頭查

為什麼要拆？因為 skill 是可以被重複叫的零件。comps-analysis 這個技能，/dcf 會用、/comps 也會用，寫一次兩邊共用。

.mcp.json 那 11 筆是外部金融資料服務的網址（S&P、Moody's、PitchBook 這種）。這個檔案就是插座。它自己沒有資料，只是寫下「要錢的話去這些地方拿」。

你可以偷學：需要多步驟、每步都要你確認的工作，用 command 寫流程；每一步真正的專業知識寫成獨立 skill。流程和知識分開，改一邊不會弄壞另一邊。
claude-video/ ├── .claude-plugin/ │ ├── plugin.json │ └── marketplace.json ← 給人裝的 ├── hooks/ │ ├── hooks.json │ └── scripts/check-setup.sh └── skills/watch/ ├── SKILL.md 268 行說明 └── scripts/ 2343 行 Python ├── download.py ├── frames.py ├── whisper.py └── …
268行說明
2343行程式
1個 hook

這是什麼：讓 AI「看」影片的技能。你丟一個 YouTube 網址給它，它就能回答影片裡講了什麼、第幾分鐘在做什麼。

程式做苦工，SKILL.md 只寫「怎麼用這些程式」

Claude 本身看不到影片。這個外掛是用 Python 程式把影片下載、切成一張張圖片、把聲音轉成文字，再把成果交給 Claude 看。

所以 268 行的 SKILL.md 幾乎全部在寫操作手冊，例如：「先跑檢查程式，回傳 2 代表工具沒裝、3 代表沒設金鑰、4 代表兩個都缺，各自要做什麼」。真正的活是程式在幹，SKILL.md 只負責看懂回傳值然後決定下一步。

那個 hook 是 SessionStart（每次開新對話時自動跑），5 秒內檢查 ffmpeg 這些工具在不在。沒問題就完全不出聲，這是好 hook 的樣子，只有壞掉才講話。

你可以偷學：會算錯的事情不要交給 Claude 用想的。數字、格式轉換、檔案處理，寫成一支 script 讓它每次跑出一樣的結果，SKILL.md 只寫什麼時候跑、跑完怎麼判讀。
03

你要做哪一種？

從最左邊開始，不夠再往右長。

Level 1

一個 SKILL.md

「有一套標準，但每次都要重講一遍」
  • 做網站的版型品味
  • 公司內部的做事規矩
  • 某個領域的判斷標準
例：imagegen。15 分鐘可以做完。
Level 2

SKILL.md + 檔案

「內容太長，或有些事不能靠猜」
  • references/：查得到但不用一直記的資料
  • scripts/：要算得準、每次一樣的事
  • assets/：範本、字體、圖檔
例：claude-video。看你會不會寫程式。
Level 3

包成 plugin

「要給同事裝，或東西多到要分類」
  • 多個 skill 互相呼叫
  • command 寫流程、skill 寫專業
  • 放 GitHub 讓人一行指令安裝
例：financial-analysis。多花 30 分鐘打包。
不要犯的順序錯誤：先建一堆資料夾、寫 plugin.json、想 marketplace，結果 skill 本身還沒寫。先寫那個 .md，確定 Claude 真的會照做，其他都是後面的事。
04

15 分鐘做出第一個 skill

下面每一段都可以直接複製貼上。

先看你等一下會做出什麼

一個技能就是一個資料夾。裡面四種東西，只有 SKILL.md 是必要的，其他三個是東西變多之後才需要。第一次做只會有一個檔案。

~/.claude/skills/ ← 放這裡的技能，所有專案都用得到 └── my-first-skill/ ← 資料夾名字就是技能的名字 ├── SKILL.md ← 唯一必要的檔案。全大寫 ├── references/ （選配）查得到就好的長資料 │ └── examples.md ├── scripts/ （選配）要算得準、每次一樣的事 │ └── check.py └── assets/ （選配）範本、字體、圖檔 └── template.docx

那個 .md 檔的內容

--- ← 三個橫線夾起來的叫 frontmatter name: my-first-skill ← 必填。跟資料夾同名 description: 使用者要寫給客戶 ← 必填。這是唯一的開關 的信時使用。也在使用者說 「幫我寫封信」時使用。 --- ← frontmatter 到這裡結束 # 寫客戶信 ← 標題，寫給人看的 ## 什麼時候用 ← 再講一次觸發時機 ## 規則 ← 你真正想交代的事 ## 產出格式 ← 叫它直接給成品

橫線裡面跟外面，讀的時機完全不一樣。Claude 平常只看得到 frontmatter 那幾行，橫線以下的全文要等它決定「這件事該用這個技能」才會載進去。

所以 description 是整份檔案裡唯一會被無條件讀到的一句話。下面第三步會專門講怎麼寫它。

建一個資料夾30 秒

名字用小寫加連字號，資料夾名字就是技能的名字。放在 ~/.claude/skills/ 底下的技能，你所有的專案都用得到。

mkdir -p ~/.claude/skills/my-first-skill

寫 SKILL.md10 分鐘

檔名一定要全大寫的 SKILL.md，寫成 skill.md 不會被認出來。最上面用三個橫線夾起來的那塊叫 frontmatter（前置資料，給機器讀的標籤），只有 name 和 description 是必填。

# 用這行把整個範本寫進檔案（含最後那個 EOF） cat > ~/.claude/skills/my-first-skill/SKILL.md <<'EOF' --- name: my-first-skill description: 使用者要寫給客戶的信、報價說明或道歉信時使用。 也在使用者說「幫我寫封信」「這樣講會不會太兇」時使用。 純內部筆記或程式註解不要用這個技能。 --- # 寫客戶信 ## 什麼時候用 使用者要對外發訊息，收件人是客戶或合作對象。 ## 規則 1. 先講結論，再講原因。不要鋪陳。 2. 一段最多三行。 3. 有壞消息時，壞消息放第一段，補救方案放第二段。 4. 不要用「我們深感抱歉」這種空話，寫具體做了什麼。 ## 產出格式 主旨一行 + 內文，直接給可以複製的成品，不要問我要不要改。 EOF

description 是唯一的開關最重要的一步

Claude 平常只看得到 name 和 description，本文要等它決定「這件事該用這個技能」才會讀進去。所以 description 寫壞，你整份技能就永遠不會被叫到。

寫成這樣 → 不會觸發

description: 幫忙寫信的技能

沒有任何「使用者說什麼算數」的線索。Claude 不知道什麼時候該想起它。
寫成這樣 → 會觸發

description: 使用者要寫給客戶的信、報價說明或道歉信時使用。也在使用者說「幫我寫封信」「這樣講會不會太兇」時使用。純內部筆記不要用。

列出實際會講的話，還寫了什麼時候不要用。三個要素：做什麼、聽到什麼觸發、什麼時候不要。

重開，然後測2 分鐘

改完一定要重開 Claude Code，它是開啟時掃一次技能清單，不會邊跑邊發現新檔案。重開後先確認它看得到：

# 在 Claude Code 裡面打這行，清單裡要出現 my-first-skill /help

然後不要直接喊技能名字，那是作弊。講一句真實情境（「幫我寫封信跟客戶說交期要延一週」），看它會不會自己想起來。不會，就是 description 還不夠具體，回上一步改。

太長就拆出去之後再說

SKILL.md 本文控制在 5000 字以內。太長的東西拆成另一個檔，本文只留一句「詳細對照表看 xxx.md」。

舉一個真的會這樣拆的例子。這個技能的工作是讓中文讀起來像台灣人寫的，不像翻譯或 AI 寫的：

tw-tech-blog-voice/ ├── SKILL.md ← 規則本身：口氣、句型、不准用破折號 └── word-swaps.md ← 80 組中國用語對照表，要查才讀

為什麼要拆：那 80 組對照表每次都塞進去很浪費，大部分時候根本用不到。所以 SKILL.md 裡只寫「最常漏掉的五個」，剩下留一句「完整對照表看 word-swaps.md」，真的要查的時候它才會去讀。

同一件事不要兩邊都寫。寫在另一個檔裡就從 SKILL.md 拿掉，不然改了一邊會忘記另一邊。

05

打包成 plugin，給別人一行指令安裝

skill 只有你自己的電腦有。要送人就得包成 plugin（外掛）。其實就是多兩個 json 檔（一種給機器讀的資料格式）加一個 GitHub repo。

照這個資料夾長相擺5 分鐘

兩條規則不能破：plugin.json 一定要在 .claude-plugin/ 裡面；其他資料夾一定要在最外層，不能塞進 .claude-plugin/。放錯位置就是整個外掛消失，而且不會噴任何錯，安安靜靜的。

my-plugin/ ├── .claude-plugin/ │ ├── plugin.json ← 必要。身分證 │ └── marketplace.json ← 要給人裝才需要 ├── skills/ │ └── my-first-skill/ │ └── SKILL.md ├── commands/ ← 沒有就不用建 ├── agents/ ← 沒有就不用建 ├── hooks/hooks.json ← 沒有就不用建 └── .mcp.json ← 沒有就不用建

兩個 json 檔3 分鐘

plugin.json 只有 name 是必填，其他都是給人看的。marketplace.json 是店面目錄，別人是先「加你的店」，再「裝店裡的東西」。

// .claude-plugin/plugin.json { "name": "my-plugin", "version": "0.1.0", "description": "一句話講清楚這個外掛做什麼", "author": { "name": "你的名字" }, "license": "MIT" }
// .claude-plugin/marketplace.json { "name": "my-marketplace", "owner": { "name": "你的名字" }, "plugins": [ { "name": "my-plugin", "description": "一句話講清楚這個外掛做什麼", "source": "./" } ] }

推上 GitHub2 分鐘

cd my-plugin git init git add . git commit -m "第一版外掛" git branch -M main git remote add origin https://github.com/你的帳號/my-plugin.git git push -u origin main

別人這樣裝30 秒

把這兩行貼給對方就好。第一行是「把你的店加進他的清單」，第二行才是「裝」。

/plugin marketplace add 你的帳號/my-plugin /plugin install my-plugin@my-marketplace

裝好之後檔案會躺在對方電腦的 ~/.claude/plugins/ 底下。你自己的電腦也可以這樣裝自己的外掛，順便驗證包得對不對。

06

五個一定會踩的坑

前四個是新手坑，最後一個是官方外掛真的踩到的。

技能做好了，但它永遠不出現

症狀
喊名字才動，講情境完全沒反應。
原因
description 寫太籠統。Claude 平常只看得到那一行。
怎麼修
把你真的會講的那句話直接抄進 description，並補一句「什麼時候不要用」。

改了半天，Claude 還在用舊版

症狀
明明改了規則，行為一模一樣。
原因
技能清單是開啟時掃一次，執行中不會重掃。
怎麼修
關掉重開。這比你想的更常是原因。

整個外掛像不存在一樣

症狀
裝了沒錯誤訊息，但什麼都沒出現。
原因
檔案放錯層。plugin.json 沒在 .claude-plugin/ 裡，或 skills/ 被塞進 .claude-plugin/ 裡面了。
怎麼修
對照第 05 節那張圖。只有 plugin.json 和 marketplace.json 在 .claude-plugin/ 裡，其他全在最外層。

SKILL.md 越寫越長，反而變笨

症狀
加了新規則，舊規則開始被忽略。
原因
本文塞太多，重點被稀釋。超過 5000 字就該拆了。
怎麼修
規則和流程留在 SKILL.md，查表、範例、長文件搬去 references/，兩邊不要重複寫。

漏一個逗號，整個檔案報廢真實案例

症狀
Anthropic 官方發布的 financial-analysis 外掛 0.1.1 版，.mcp.json 裡 egnyte 那段結尾少一個逗號，下一段 box 又少一個結尾大括號。整個檔案不是合法 JSON，那 11 個金融資料來源一個都接不上。
原因
JSON 這種格式，逗號和括號錯一個字元就整份失效，而且它通常不會跳出紅字告訴你，只是安靜地什麼都沒發生。
怎麼修
改完 json 檔就跑一次這行，會直接指出第幾行有問題：
python3 -m json.tool 你的檔案.json
下一步只做一件事：想一句你這個月已經對 Claude 重複講過三次以上的話，把它寫成 SKILL.md 的第一條規則。一條就好，其他的用著用著自己會冒出來。
