點選檔案樹中的項目，查看說明與修改注意事項。

02

依檔案的來源判斷修改方式

檔案的來源會影響維護方式。以下分類有助於初步判斷；設定檔與機密資料仍需依專案規則處理。

原始檔

由開發者維護的原始內容。

包含程式碼、文件與設定。修改後需測試，並透過 Git 提交要與團隊共享的變更。

  • src/
  • public/
  • README.md
  • package.json
  • 各種 .config 設定檔

工具產生的

通常應修改來源，再重新產生。

這些檔案由建置或安裝工具產生。直接修改可能在下次執行工具時被覆寫；鎖定版本的檔案則通常需要納入版本控制。

  • dist/ · build/ · .next/
  • package-lock.json
  • *.d.ts（自動產生的型別檔）
  • coverage/（測試報告）

工具管理的

透過管理工具更新，避免直接修改。

包含第三方套件與版本控制資料。套件的本機修改不會自動共享；Git 內部資料則應透過 Git 指令管理。

  • node_modules/
  • vendor/
  • .git/（Git 自己的紀錄）
.gitignore 是輔助線索。它列出 Git 應忽略的未追蹤檔案，可能包含建置產物、本機設定或機密資料。
被忽略不代表不需維護。例如 .env 常需要在本機設定，但不應提交含有密鑰的內容。
03

熟悉新專案的閱讀順序

先理解專案如何啟動，再追蹤畫面與程式碼的對應關係。以下時間僅供初步瀏覽安排；環境安裝與問題排查可能需要更久。

先讀 README.md3 分鐘

README 通常介紹專案目的、安裝條件與啟動方式。若資訊不足，可搭配設定檔與近期提交紀錄確認，不能只憑文件完整度判斷維護狀況。

看 package.json 的 scripts2 分鐘

scripts 列出專案定義的指令。冒號左側是名稱，右側是實際執行內容。執行前先確認指令的用途。

"scripts": { "dev": "vite", ← npm run dev 開發模式 "build": "tsc && vite build", ← npm run build 打包上線 "test": "vitest" ← npm run test 跑測試 }

找進入點3 分鐘

找出應用程式的進入點，再沿著匯入關係閱讀。常見名稱有 main 或 index；App 通常是根元件。使用框架時，也可能由框架管理進入點。

啟動本機開發環境5 分鐘

依 README 安裝相依套件並啟動。若需要 .env，可參照 .env.example 建立本機設定，填入自己有權使用的服務資訊。下列指令適用於使用 npm 且定義了 dev script 的專案。

npm install npm run dev

以一處文字修改確認檔案對應2 分鐘

找出畫面上的一段文字，修改後檢查瀏覽器是否更新。這能確認目前的檔案、開發伺服器與畫面是否對應。測試完成後，可還原這次修改。

04

修改前需要留意的檔案

以下項目各有管理方式。先確認其用途，能降低覆寫、版本不一致或資料外洩的風險。

node_modules/
第三方套件的安裝位置。直接修改不會自動進入團隊的安裝流程，也可能被重新安裝覆寫。優先使用套件設定；若需修補原始碼，應採用可追蹤、可重現的修補流程。
package-lock.json
記錄相依套件的確切版本與解析結果。通常應交由 npm 更新並提交變更。任意修改或刪除可能改變安裝結果；重現既有環境時，可使用與鎖檔一致的 npm ci。
dist/ · build/
建置工具產生的輸出。應先修改來源檔，再重新建置。直接修改輸出檔可能在下次建置時被覆寫。
.git/
儲存本機儲存庫的物件、參照與設定。刪除可能失去尚未推送的提交與本機資訊。遠端或備份中的紀錄可能仍可恢復，但不能假設本機內容都有備份。
.env（機密設定）
可能包含 API 金鑰、密碼與連線資訊。避免提交或公開分享有效的機密值。若已外洩，應先撤銷並更換憑證，再清理公開內容與相關紀錄；單純刪除檔案無法使舊憑證失效。

延伸閱讀：Git 忽略規則、npm 鎖檔安裝。

閱讀新專案時，可從 README 與啟動指令建立方向，再沿著進入點追蹤程式。
修改檔案前，確認它的來源、產生方式與版本控制規則。
