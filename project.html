02

只要分成三種就好

看到一個沒見過的檔案，先問一句：這是誰放的？答案只有三個，而且對應三種完全不同的態度。

你寫的

改這裡。這是你的工作區。

你打字打出來的東西。改了會生效、會被 Git 記錄、會被別人看到。

  • src/
  • public/
  • README.md
  • package.json
  • 各種 .config 設定檔

機器產生的

改了會被蓋掉。白費工。

從「你寫的」自動生出來的。你改它就像改影印本，原稿一印，你的改動就沒了。

  • dist/ · build/ · .next/
  • package-lock.json
  • *.d.ts（自動產生的型別檔）
  • coverage/（測試報告）

別人的

完全不要進去。

從網路下載來的套件。你改了，別人重裝就沒有，等於你一個人在演。

  • node_modules/
  • vendor/
  • .git/（Git 自己的紀錄）
怎麼快速分辨？打開 .gitignore，裡面列出來的，全部都是「產生的」或「別人的」。
因為 Git 不記錄它們。不需要記錄的東西，就是不需要你改的東西。
03

拿到一個陌生專案，照這五步

不要一打開就從第一個檔案開始讀。照順序來，15 分鐘就能摸清楚一個中型專案。

先讀 README.md3 分鐘

這是專案的說明書：它是什麼、怎麼跑起來、要先裝什麼。寫得爛的 README 也有資訊，代表這專案可能沒人維護。

看 package.json 的 scripts2 分鐘

這段告訴你這個專案能打哪些指令。冒號左邊是指令名，右邊是它實際會做的事。

"scripts": { "dev": "vite", ← npm run dev 開發模式 "build": "tsc && vite build", ← npm run build 打包上線 "test": "vitest" ← npm run test 跑測試 }

找進入點3 分鐘

整個程式從哪一行開始跑。通常在 src/ 裡面，叫 main、index 或 App。從它往下讀，比隨便亂翻有效十倍。

真的把它跑起來5 分鐘

讀十遍不如跑一遍。如果需要 .env，看看有沒有 .env.example 可以照抄。

npm install npm run dev

改一個字，確認畫面真的會變2 分鐘

隨便找一段畫面上看得到的文字，改掉它，看瀏覽器有沒有跟著變。這一步是在確認「你改的檔案，就是你看到的畫面」。很多人卡好幾小時，最後發現一直在改錯的檔案。

04

這五個絕對不要動

這五個動了會出事，而且不好救。

node_modules/
下載來的套件，幾萬個檔案。你改的東西別人完全看不到，因為他重裝就蓋掉了。要改套件行為，用官方提供的設定，不要動原始碼。
package-lock.json
手改會讓「鎖版本」失效，導致你的電腦跟伺服器裝到不同版本。那種「我這邊明明好好的」就是這樣來的。要改就改 package.json，然後 npm install 讓它自己更新。
dist/ · build/
打包產生的成品。下次 build 會整包蓋掉，你的改動一秒消失。要改就去改 src/ 裡的原稿。
.git/
Git 的全部歷史紀錄都在這個資料夾裡。刪掉等於所有版本紀錄永久消失，沒有任何辦法救回來。它看起來只是個隱藏資料夾，但它是整個專案的記憶。
.env（別人的）
裡面是密碼和金鑰。不要上傳、不要貼給任何人、不要放進截圖。真的外洩了，正確做法是去服務商後台把那把金鑰作廢重發，光刪掉檔案沒有用，它已經在 Git 歷史裡了。

一句話帶走：看到不認識的檔案，先打開 .gitignore。
在裡面 ＝ 不用管它。不在裡面 ＝ 有人刻意寫的，值得看一眼。
